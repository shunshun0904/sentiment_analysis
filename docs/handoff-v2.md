# 株式市場センチメント可視化アプリ 開発引き継ぎプロンプト（v2）

> 前版（`sentiment_dashboard_引き継ぎプロンプト.md`）を置き換える。
> 最終更新: 2026-08-15

あなたには、以下の設計方針が確定済みのプロジェクトを引き継いで開発を支援してもらいます。
方針は議論済み・合意済みなので、蒸し返さずにこの前提で進めてください。

---

## プロジェクト概要

- 株式市場のセンチメントを可視化するブラウザアプリを作る
- 対象は **指数のみ**（S&P500、日経平均など）。個別銘柄は対象外
- まず米国側（S&P500）から着手し、日経は後続
- **目的は「市場全体のムード」の可視化**であって、指数の厳密な再現ではない
  （時価総額加重による指数センチメントの再構成は検討したうえで**不採用**）

---

## 確定済みのアーキテクチャ

**Lambda + EventBridge + S3 のサーバレス構成**

```
EventBridge(60分スケジュール)
  → Lambda(取得 → 重複排除 → ソースフィルタ → 集計 → S3へ履歴JSON追記)
  → S3(履歴JSON保存 + SPA静的ホスティング)
  → ブラウザSPA(S3のJSONをfetch)
```

- ブラウザ完結構成は却下済み（履歴が途切れる、APIキー露出、LLM組込み困難）
- EC2常時起動も却下済み（月約600円で過剰）

### 更新頻度を 5分 → 60分 に変更した（v1からの重要変更）

理由:

1. **ポーリング頻度＝遅延であって、チャートの時間解像度ではない。**
   記事には `time_published` が付くため、60分に1回まとめて取得しても
   5分刻みの時系列はSPA側で再構築できる。失うのは最大60分の鮮度だけ
2. 5分更新は元データの流量に対して過剰だった
3. 無料枠で「リアルタイム × 十分なリクエスト数 × センチメント付き」を
   同時に満たすAPIが事実上存在しないため

用途としてはイベント時（FOMC・CPI等）の急変検知も視野にあるが、
60分遅延を理解したうえで許容する判断がなされている。

## データソース: Alpha Vantage `NEWS_SENTIMENT`（確定）

無料枠 **25リクエスト/日**、5リクエスト/分。60分間隔なら成立する。

**v1の「無料25req/日で288回/日に届かないため除外」という判断は、
更新頻度を60分に落としたことで無効になった。**

### 取得方法

```
function=NEWS_SENTIMENT
topics=financial_markets,economy_macro,economy_monetary
time_from=<前回実行時刻 - 15分>
limit=1000
sort=LATEST
```

## 実測で確認した事実（2026-08-15 に Alpha Vantage を実際に叩いて検証）

以下は推測ではなく実レスポンスから確認した内容。**この章の数字は上書きしないこと。**

| 項目 | 実測値 |
|---|---|
| 記事数 | `topics=financial_markets` の1時間窓（2026-08-14 13:00–14:00 UTC）で **206件** |
| `limit` 上限 | 1000。1時間分は1リクエストに収まる |
| レスポンス容量 | 206件で約99,000トークン相当。S3保存前のフィールド削減が必須 |
| 重複排除キー | 記事IDフィールドは無い。`url` が事実上の主キー |

### 1. `tickers` パラメータは OR ではなく **AND**

| クエリ | 件数 |
|---|---|
| `NVDA` | 6件 |
| `NVDA,AAPL` | 1件（両方に言及した記事のみ） |
| 主要15銘柄 | **0件** |

**銘柄バスケットを1リクエストで取ることはできない。**
1銘柄1リクエストが必要になり、25req/日の枠では成立しない。
時価総額加重方式を断念した直接の理由。

なお `topics` クエリのレスポンスにも全記事に `ticker_sentiment` が付いているため、
将来どうしても銘柄別の分解が必要になれば、クォータを増やさずに集計側で対応できる。

### 2. スコアの範囲についての訂正

v1の資料に「スコアは精緻(-0.35〜+0.35)」とあったが**これは誤り**。
-0.35 / +0.35 は Bearish / Bullish の**ラベル閾値**であって上下限ではない。
実測で `0.434062` の記事を確認している。理論上の上下限はAPIに明示がないため要観察。

正しいラベル定義:
```
x <= -0.35            : Bearish
-0.35 < x <= -0.15    : Somewhat-Bearish
-0.15 < x < 0.15      : Neutral
0.15 <= x < 0.35      : Somewhat_Bullish
x >= 0.35             : Bullish
```

### 3. 同一記事が複数ドメインから配信される

`stockstotrade.com` と `timothysykes.com` が**同一タイトル・同一時刻**で
同じ記事を配信している例を確認。URLだけで重複排除すると二重計上する。
→ URL と正規化タイトルの**二重キー**で排除する設計にした。

### 4. ノイズ源の存在

取得記事の上位が**アルゴ自動生成記事**で占められていた。
確認できた `source_domain`:

```
Stock Traders Daily / StocksToTrade / Timothy Sykes /
GuruFocus / Simply Wall Street / 24/7 Wall St. / TradingView
```

個別ETFの機械的テクニカル分析などが大量に出るため、
そのまま平均すると市場センチメントが希釈される。
→ ホワイトリスト方式のソースフィルタを実装（後述の「観測モード」で運用開始）

## 却下したデータソース（再検討不要）

| API | 却下理由 |
|---|---|
| **APITube** | 無料枠が**12時間遅延**（ユーザーが実測確認）。リアルタイム不可 |
| **finlight** | 無料枠が同じく**12時間遅延**、かつセンチメント非提供 |
| **Polygon (現Massive)** | ニュースが**全プラン1時間更新**、センチメントはカテゴリのみで数値なし |
| **Marketaux** | 即時・センチメント数値ありだが**3記事/リクエスト**が律速。頻度を上げても記事数が増えない |
| **Finnhub** | 60コール/分・リアルタイムだが、**汎用ニュースにセンチメントが付かない**。LLMスコア化と組み合わせる案（後述）は不採用 |

### APITube の公表値についての注意

APITube のサイト内に無料枠の値が **100 / 200 / 1,000 req/日 の3種類が併存**している。
ヘルプセンター（技術文書・2026-08-09更新）と料金表本体が一致する **100req/日** が正。
FAQ や `free-news-api` ページの数値は旧情報。**マーケティング用ページの数値は信用しないこと。**

### Finnhub + Claude Haiku 案を不採用にした経緯

一時は「Finnhubで取得し、Claude Haiku 4.5（$1/百万入力・$5/百万出力）で
自前スコア化する」案を推奨していた。しかし実測で記事流量が
**1時間で206件**（＝1日数千件規模）と判明し、v1資料の「300〜500記事/日」想定が
約1桁過小だったことが分かった。この流量ではHaiku費用が月$20〜30規模になり、
「月0〜150円」の前提から大きく外れるため不採用。

**Alpha Vantage のスコアが無料である以上、記事数が増えてもコストが増えない点が決定的。**

## センチメント算出方式

記事単位の時間減衰加重平均。

$$S(t) = \frac{\sum_j d_j \cdot r_j \cdot s_j}{\sum_j d_j \cdot r_j}$$

- $j$: 記事
- $s_j$: `overall_sentiment_score`
- $r_j$: `topics` のうち market 系トピック（`financial_markets` / `economy_macro` /
  `economy_monetary`）の `relevance_score` の最大値
- $d_j$: 時間減衰 $0.5^{\Delta t / T_{1/2}}$、半減期 6時間（暫定）

**対照系列として単純平均（`raw_mean`）を必ず併記する。**
主系列と乖離したときに、減衰や relevance の設定を疑うための基準になる。

### スコア算出部は差し替え可能に保つ

集計ロジックは `score.py` に閉じている。将来LLMベースのスコアに
差し替える場合も、入出力の形を保てば他モジュールに変更は要らない。

## クォータ管理（無料枠 25req/日）

- 毎時実行だと24回で予備が1回しかないため、**UTC 5時・6時を間引いて22回/日**に
- 予備3回を確保
- **失敗時のリトライはしない**（クォータを消費して翌日分を削るリスクのほうが大きい）
- `state/last_run.json` で使用回数を自己管理し、上限に達したらスキップ

Alpha Vantage は HTTP 200 のままエラーを本文で返す点に注意。
レート超過は `Note` / `Information`、パラメータ不正は `Error Message` キー。

## 実装済みのコード

以下6ファイルが作成済み。モジュール分割済みで、そのまま引き継げる。

| ファイル | 役割 |
|---|---|
| `handler.py` | Lambda エントリポイント。パイプラインの結線 |
| `config.py` | 全パラメータ。トピック、クォータ、減衰、S3キー |
| `fetch.py` | Alpha Vantage クライアント。ウィンドウ計算、クォータ確認 |
| `dedup.py` | 重複排除（URL＋タイトル）、ソースフィルタ、レコード削減 |
| `score.py` | センチメント集計。**差し替え対象はここだけ** |
| `store.py` | S3 読み書き、SSMからのキー取得、`public/latest.json` 生成 |
| `SCHEMA.md` | S3 JSONスキーマ定義 |

### S3構成

```
state/last_run.json                実行状態
state/seen.json                    重複排除キャッシュ（48時間ローリング）
history/sentiment.jsonl            センチメント時系列（追記）
history/articles/YYYY-MM-DD.jsonl  採用記事の監査ログ
public/latest.json                 SPAが取得する唯一のファイル
observe/sources.json               source_domain の出現頻度
```

## 未確定・要検証の項目

1. **無料枠で `NEWS_SENTIMENT` が叩けるか未確認**
   今回の検証はMCP接続経由のキーで実施しており、そのキーのプランが不明。
   プレミアム限定なのはリアルタイム株価・イントラデイ・オプション系で、
   Alpha Intelligence（ニュース・センチメント）は無料枠に含まれるはずだが、
   **自分の無料キーで1回叩いて確定させること**

2. **`time_published` のタイムゾーン**
   `time_from` / `time_to` と同一の時計系であることは実測確認済みだが、
   UTC か US/Eastern かは未確認。当面UTCとして扱っている

3. **`SOURCE_WHITELIST` は空のまま「観測モード」で開始**
   全件通しつつ `observe/sources.json` に `source_domain` の分布を蓄積する。
   数日運用してから確定する。実測で見えたのは7ドメインのみで、これで決めるのは早すぎる。
   ブラックリスト方式は新種のスパムに追随できないため採らない

4. **`HALF_LIFE_HOURS = 6.0` は暫定値**
   数日運用してS&P500の実際の値動きと目視比較してから調整する

5. **`MIN_TOPIC_RELEVANCE = 0.30` も暫定値**

## ユーザーの作業スタイル（遵守事項）

- **結論を先に述べ、詳細は後**
- 簡潔で視覚的な説明（図・表・数式）を好む。冗長なテキストは避ける
- **調査して項目を列挙する際は、出力前に実在するものか自分で再確認すること。**
  架空のツール・API・文献を報告に含めない
  （自然科学分野の未検証の仮説は根拠付きなら可）
- 前提が崩れたら黙って代替せず、**崩れたことを明示して選択肢を提示する**
- 資料の記載に誤りを見つけたら訂正して報告する
- AWS（Lambda、EventBridge、S3、SSM等）の実務経験があるため基礎説明は不要
- Pythonのモジュール分割されたコードベースが標準形式
- 暫定値・未検証項目はコード中のコメントとドキュメントの両方に明記する
